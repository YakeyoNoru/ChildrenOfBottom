## 개선 순서

1. **실패 진단을 먼저 개선한다.** 현재 소켓 테스트 도우미 `next(type)`는 메시지 종류만 비교하고 2초 후 그 종류만 출력한다. 명령 응답을 `requestId`로 연결하고, 기대한 응답과 실제 응답이 다르면 즉시 보여준다. 대기 실패에는 명령명, 참가 순번, 마지막 몇 개의 메시지 유형, 소켓 종료 코드 및 종료 시각을 남긴다. 인증 값과 재접속 토큰은 출력하지 않는다.
2. **카운트다운을 우선 조사한다.** 가상 방 시각을 599999ms에서 600000ms로 넘길 때 모든 참가자에게 `game.result`가 한 번씩 전달되고 이유가 `TIME_LIMIT`이어야 한다. `server.js`의 시뮬레이션, `finishPlayer`, `send`를 차례로 확인한다. 5인 초기 스냅샷 이후 송신 버퍼가 65536바이트를 넘으면 `send`가 연결을 종료하는 경로가 있으므로, 종료 여부와 직전 버퍼 크기를 측정한다. 현재로서는 검증할 가설이다. 병목이 확인되면 낡은 상태 스냅샷을 합치는 방안을 우선 검토하고, 결과·응답 이벤트 전달과 느린 연결의 메모리 제한을 함께 검증한다.
3. **전체 실행에서만 드러난 두 건을 분리한다.** 진단을 붙인 뒤 시나리오별 반복과 전체 실행을 Windows 및 GitHub Linux에서 비교한다. 맵이나 월드의 무작위 상태가 재현에 영향을 주는지 확인하고, 관련이 확인되면 고정 시드 또는 최소 월드로 검증한다. 제한 시간만 늘려 실패를 가리지 않는다.

완료 기준은 세 시나리오와 전체 테스트 통과, 5인 전원 결과 수신, 일반 참가자의 테스트 옵션 거부 및 기술 구매 규칙 유지다. 보스 복귀 회귀 테스트도 유지한다.
